## 1. `admin_screen_test.dart`

Couvrir (lecture de `lib/ui/admin_screen.dart` faite — comportements
réels) :
- Chargement initial : `GET /admin/users` → liste d'utilisateurs
  affichée (un `ListTile` par user, icône `person`/`person_off` selon
  `is_active`, sous-titre avec/sans préfixe `admin · `).
- Erreur de chargement : `GET /admin/users` → 500 ou réponse qui lève
  `ApiException` → `_error` affiché en bas (`bottomSheet`, texte rouge)
  au lieu de planter.
- Créer un compte : tap FAB → dialog → remplir email/password → tap
  « Créer » → `POST /admin/users` avec le bon body → dialog fermé +
  liste rechargée. Double-submit (`_creating` guard) : NE PAS tester le
  double-tap réel nécessairement si trop complexe à simuler de façon
  fiable en widget test — au minimum un test qui pose `_creating=true`
  via l'état et vérifie qu'un second appel au handler ne déclenche pas
  un second POST (ou documenter si non testable simplement et pourquoi).
- Toggle actif/admin via le menu ⋮ d'un user : `PATCH
  /admin/users/<id>` avec `{"is_active": ...}` ou `{"is_admin": ...}` →
  liste rechargée.
- Reset password : action « reset » du menu → dialog → `PATCH
  /admin/users/<id>` avec `{"password": ...}`.

## 2. `share_screen_test.dart`

Couvrir (lecture de `lib/ui/share_screen.dart` faite) :
- Chargement initial : `GET /lists/<id>/members` → membres affichés
  (icône `stars` pour owner sans menu de rôle/suppression, `person`
  pour les autres AVEC menu).
- Générer un code d'invitation : tap « Générer » → `POST
  /lists/<id>/invites` (body `{"hours": 48}`) → le code s'affiche, tap
  dessus → `Clipboard` + SnackBar `S.codeCopied` (vérifier au moins
  l'affichage du code et le SnackBar ; le contenu réel du presse-papier
  n'est pas forcément vérifiable en widget test selon l'environnement
  — documenter si skippé).
- Ajouter un membre par email : remplir le champ + choisir un rôle +
  tap bouton → `POST /lists/<id>/members` avec `{"email": ..., "role":
  ...}` → champ vidé + liste rechargée. Email vide → `_addMember` ne
  fait rien (pas d'appel réseau).
- Changer le rôle d'un membre (non-owner) : dropdown → nouvelle valeur
  → `PATCH /lists/<id>/members/<user_id>` avec `{"role": ...}`.
- Retirer un membre : tap icône suppression → `DELETE
  /lists/<id>/members/<user_id>` → liste rechargée.
- Erreur réseau sur une des actions ci-dessus → `_error` affiché (texte
  rouge en bas de la liste), pas de crash.

## 3. SyncService — gaps de couverture

Lire `lib/data/sync_service.dart` (`_chunkSize = 500` ligne ~41,
`_postEvents` ligne ~128-141, `_scheduleReconnect` ligne ~365-375)
avant d'écrire les tests. Deux tests ciblés, fichier existant
`sync_service_test.dart` si trouvé par `search_files`, sinon nouveau
`sync_service_chunking_test.dart` :

- **Chunking** : construire une liste de > 500 events (ex. 1200) à
  pousser via le chemin qui appelle `_postEvents` (lire comment les
  tests existants déclenchent un push — suivre leur pattern plutôt que
  d'inventer un accès direct à une méthode privée si l'API publique le
  permet déjà). Un `MockClient` qui compte les requêtes `POST /sync`
  reçues → vérifier que le nombre d'appels est `ceil(1200/500) = 3`,
  PAS 1 (preuve que le chunking produit bien plusieurs requêtes, pas
  une seule avec tout dedans).
- **Backoff reconnect** : `_scheduleReconnect` est privée — si les
  tests existants ont déjà un seam pour observer/forcer des échecs de
  connexion répétés (chercher comment le test actuel « pas de doublon
  » déclenche une reconnexion), réutiliser ce seam pour vérifier la
  PROGRESSION du délai (pas juste qu'une reconnexion a lieu) : au moins
  2-3 échecs successifs → le délai programmé croît (via un
  `FakeAsync`/horloge contrôlée si le projet en a déjà l'habitude pour
  ce fichier, cf. pattern `fake_async` déjà utilisé ailleurs dans la
  suite pour des délais). Si aucun seam n'existe et qu'en ajouter un
  exigerait de changer le code de production (hors périmètre de cette
  spec, additive uniquement) : documenter précisément pourquoi ce point
  est reporté plutôt que d'inventer un accès à l'implémentation privée
  qui casserait au moindre refactor interne.
